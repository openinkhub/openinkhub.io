Server-side rendering means the server builds the complete HTML for a page each time someone requests it, then sends it to the browser. It is the right choice when pages must show fresh, frequently changing or personalised information, such as live prices, stock levels, search results, dashboards or account pages, while still giving search engines complete HTML. Server-side rendering usually costs more to host than static pages, because servers work on every request, but smart caching keeps that cost under control.

When to choose server-side rendering

Page typeWhy SSR helps
Product pages with live stock or pricesAlways accurate data
Search and filter resultsIndexable, shareable result pages
Personalised pagesContent based on the logged-in user or location
News and listings that change oftenNo waiting for rebuilds
Very large sitesNo need to pre-build millions of pages

How server-side rendering works

  1. A visitor or search engine requests a page.
  2. The server fetches data from databases or APIs.
  3. It renders the full HTML and sends it.
  4. The browser shows content immediately, then JavaScript makes it interactive.

Frameworks such as Next.js, Nuxt and SvelteKit handle this. Next.js documents its options in the rendering guide.

SSR and SEO

Because search engines receive complete HTML, server-rendered pages are indexed reliably, unlike client-only apps. Many AI crawlers also read only raw HTML. However, slow servers hurt Largest Contentful Paint, so performance work is essential. Our JavaScript SEO guide explains rendering and indexing in detail.

Keeping SSR fast and affordable

  • Cache full pages or data for a short time where freshness allows.
  • Stream parts of the page so visitors see content sooner.
  • Run rendering close to users with edge functions where it fits.
  • Keep database queries fast and indexed.
  • Render only what must be dynamic; make the rest static.

Our guide to edge computing explains how rendering near users cuts delay.

SSR vs SSG

Static site generation is cheaper and faster for content that rarely changes. Server-side rendering is better for fresh and personalised pages. Most modern sites mix both: static marketing and blog pages, and server-rendered product, search and account pages. See our static site generation guide for the other side.

What it costs

Build costs are similar to other modern framework projects. Hosting costs more than static hosting because of server work, and usage-based platforms charge for function time. Good caching often cuts that cost dramatically. Therefore, ask any partner to estimate hosting costs at your expected traffic.

Choosing a partner

Ask for live server-rendered sites and test their speed. Ask which pages they would render on the server and why, and how they cache them. Check monitoring for server errors and slow responses. Finally, confirm ownership of hosting accounts and code.

Common mistakes

First, rendering every page on the server when most could be static. Next, no caching, which raises costs and slows pages. Then, slow database calls blocking the whole page. Finally, ignoring error handling, so one failed API breaks the page.
