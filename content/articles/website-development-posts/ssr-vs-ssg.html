SSR vs SSG is a choice about when your web pages are built. With server-side rendering (SSR), the server builds each page when a visitor requests it, so content is always fresh and can be personalised. With static site generation (SSG), pages are built once at deploy time and served from a CDN, so they are the fastest and cheapest to deliver. Use SSG for pages that rarely change, such as blogs and service pages. Use SSR for pages that must be up to date on every visit.

SSR vs SSG at a glance

SSRSSG
When the page is builtOn each requestAt build or deploy time
FreshnessAlways currentCurrent as of last build
SpeedFast, but needs server workFastest, served from CDN
Server costHigherVery low
PersonalisationEasyLimited, done in the browser
Best forDashboards, live stock, search resultsBlogs, docs, marketing pages

SEO

Both methods send complete HTML to search engines, so both are SEO-friendly, unlike pages that render only in the browser. SSG often has a slight edge, because pre-built pages from a CDN load very quickly, which helps Core Web Vitals. SSR is also good for SEO as long as the server responds fast. Google explains the trade-offs in its rendering on the web guide.

Performance

SSG pages are ready before anyone asks for them, so the time to first byte is tiny. SSR pages need the server to fetch data and build HTML for each request, which adds time, especially under heavy load. However, caching SSR responses at the CDN narrows the gap. For pages like a product listing that changes hourly, cached SSR can be a good compromise.

The hybrid option

Modern frameworks let you mix both. In Next.js, for example, each page can be static, server-rendered or statically generated with periodic refresh, often called incremental static regeneration. This means a blog post can be static, a product page can refresh every few minutes, and a cart page can render on every request. Our guide to Next.js website development covers this in more depth.

When to choose each

  • Choose SSG for blogs, documentation, landing pages, service pages and most marketing content.
  • Choose SSR for personalised pages, real-time prices or stock, search results and logged-in areas.
  • Choose hybrid for ecommerce and large sites with a mix of page types.

How this compares with WordPress

A traditional CMS such as WordPress renders pages on the server for each visit, which is a form of SSR, and caching plugins turn popular pages into near-static copies. So the same ideas apply even if you never touch a JavaScript framework.

Common rendering mistakes

First, using SSR for pages that never change, which wastes server money. Next, using SSG for pages with prices or stock that change constantly, which shows stale data. Then, very long builds on big static sites without incremental builds. Finally, rendering key content only in the browser, which hurts SEO.

Choosing for your project

Map each page type by how often it changes and whether it is personalised; the SSR vs SSG decision then becomes clear page by page.
